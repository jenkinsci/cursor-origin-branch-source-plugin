= Cursor Origin Branch Source Plugin — Design Notes
:toc:
:toc-placement: preamble

A Jenkins Branch Source plugin that discovers and builds branches and pull requests
from https://cursor.com[Cursor Origin] repositories.

== Goals and Non-Goals

=== In scope (v1 demo)
* Authenticate to the Origin REST API as a Cursor Origin App (JWT → installation access token).
* `OriginSCMSource`: discover branches and pull requests in a single repo.
* `OriginSCMNavigator`: discover all repos in a team namespace matching a regex.
* Polling-based trigger (no webhooks yet).
* HTTPS git checkout using the same app installation token (Basic auth: `x-access-token` / token).
* Reporting build status to Origin as a check run, via the Jenkins checks API.

=== Out of scope for now
* Webhooks, including the `check_run` re-request event (so no "re-run" button).
* Batch check-run upserts (`POST /check-runs:batchUpsert`), which would let a parallel pipeline
  report up to ten stages for the cost of one write.
* `deadlineAt` on a check run (Origin would then time the check out on its own).
* Tag discovery.
* SSH checkout.
* Rate limiting, caching, lazy iterables.
* Avatars.
* Personal access tokens (only `CursorOriginAppCredentials`).

== Authentication

`CursorOriginAppCredentials` already exists.
It implements `StandardUsernamePasswordCredentials`:
* `getUsername()` → `"x-access-token"`
* `getPassword()` → a freshly-minted installation access token (JWT exchange via REST).

Git HTTPS clone uses Basic auth with these values; the Origin git server at
`origin.cursor.com` explicitly requires Basic auth (Bearer is rejected).
`AbstractGitSCMSource` handles credential injection automatically via standard Jenkins git credential support.

== Class Structure

=== `OriginSCMSource extends AbstractGitSCMSource`

Fields:
* `String credentialsId`
* `String repoOwner`
* `String repository`
* `List<SCMSourceTrait> traits` (initially: `BranchDiscoveryTrait`, `PullRequestDiscoveryTrait`)

Key methods:
* `getCredentialsId()` → `credentialsId` (required by `AbstractGitSCMSource`)
* `getRemote()` → `https://origin.cursor.com/OWNER/REPO.git`
* `retrieve(SCMSourceCriteria, SCMHeadObserver, SCMHeadEvent, TaskListener)` — drives REST discovery

`retrieve()` flow:
1. Mint token via `CursorOriginAppCredentials`.
2. If PR discovery enabled: fetch PR list (open only) and record PR head branch names.
3. If branch discovery enabled: for each branch — skip if its name is a PR head branch,
   otherwise create plain `SCMHead` + `SCMRevisionImpl(sha)` and call `request.process()`.
4. If PR discovery enabled: for each open PR — create `OriginPullRequestSCMHead` +
   `OriginPullRequestSCMRevision` and call `request.process()`.

=== `BranchSCMHead`

Standard `jenkins.scm.api.SCMHead` subclass, name = branch name.
Revision = `AbstractGitSCMSource.SCMRevisionImpl` (single commit SHA).

=== `PullRequestSCMHead`

Extends `SCMHead`, name = `PR-<number>`.
Holds: PR number (string), head branch name, head SHA, base branch name, base SHA.

Since Origin has no forks, the PR head branch is always in the same repo.
Checkout uses `refs/heads/<headBranch>` pinned to the head SHA from PR metadata.

=== `PullRequestSCMRevision`

Holds head `SCMRevisionImpl` + target branch name + target SHA.
Does not implement merge mode.

=== `OriginSCMSourceContext / OriginSCMSourceRequest`

Thin wrappers (modelled on GitHub equivalents) that carry `wantBranches` / `wantPRs` booleans
populated from traits, plus the list of `SCMSourceTrait` instances.

=== `OriginSCMBuilder extends GitSCMBuilder<OriginSCMBuilder>`

Builds the `GitSCM` checkout step.
* Branch checkout: `+refs/heads/<name>:refs/remotes/origin/<name>`
* PR HEAD checkout: depends on whether Origin exposes `refs/pull/NNN/head`; otherwise use head branch refspec.

=== `OriginSCMNavigator extends SCMNavigator`

Fields:
* `String repoOwner` (team slug)
* `String credentialsId`
* `String pattern` (regex, default `.*`)
* `List<SCMSourceTrait> traits`

`visitSources()` flow:
1. Call `GET /v1/origin/installation/repos` (lists repos the installation has access to).
2. Filter by `repoOwner` + name matches `pattern`.
3. For each matching repo, call `observer.observe(new OriginSCMSource(...))`.

Alternatively use `GET /v1/origin/repos/{ownerSlug}` (namespace listing).
See <<_open_questions>>.

=== Traits

`BranchDiscoveryTrait`::
  Simple on/off.

`PullRequestDiscoveryTrait`::
  HEAD-only (no merge mode).
  When enabled, the branch loop in `OriginSCMSource.retrieve()` skips any branch whose name
  matches the head branch of an open PR, so each origin PR appears exactly once (as `PR-N`)
  rather than twice (branch + PR).

`OriginChecksTrait`::
  Configures how build status is reported as a check run: the check name, whether to skip
  reporting, whether an unstable build is neutral rather than a failure, whether to include the
  build log, whether to report progress as well as the final result, and whether to explain in the
  build log why nothing could be published.
  Checks are reported without the trait too; it only overrides the defaults.

== Checks

Build status is reported through the `checks-api` plugin rather than directly, so anything that
publishes checks — the automatic build status check, the `publishChecks` and `withChecks` pipeline
steps, warnings-ng — reaches Origin without knowing about it.

=== Classes (package `checks`)

`OriginChecksPublisherFactory extends ChecksPublisherFactory`::
  `@Extension`. Claims a job when its SCM source is an `OriginSCMSource` with resolvable
  credentials and a resolvable head SHA, and declines it otherwise; the checks API asks every
  registered factory in turn and takes the first that claims the job.

`OriginChecksContext`::
  Resolves the repository, head SHA, credentials, build URL and the suite/check identities.
  Created either from a `Run` (revision read from the build's `SCMRevisionAction`) or from a `Job`
  while the build is still queued (revision fetched from the source, so this path costs one API
  call).

`OriginChecksDetails`::
  Translates `ChecksDetails` into `CheckRunInput` / `CheckRunOutput` / `CheckRunAnnotationInput`,
  enforcing the parts of the Origin contract that the checks API does not: a conclusion exactly
  when the status is `completed`, a 255-character title, a 65535-byte summary and text, and a
  column range only on a single-line annotation.

`OriginChecksPublisher extends ChecksPublisher`::
  `POST /check-runs`, then any new annotations. Never throws: a failure to report is logged to the
  build log and the system log, since it must not fail the build being reported on.

`OriginStatusChecksProperties extends AbstractStatusChecksProperties`::
  `@Extension`. Without it the checks API publishes nothing automatically, so this is what turns
  the queued / in-progress / per-stage / completed reports on, named from `OriginChecksTrait`.

`OriginChecksAction extends InvisibleAction`::
  Remembers, per check of a build, how many annotations Origin has already accepted.

=== Identity and idempotency

Origin upserts a check run on `(repository, head SHA, suite key, check key)`, so each publish is one
self-contained request and there is no create-then-update distinction to track.

`checkSuite.key`::
  Full name of the multibranch project (the SCM source owner), falling back to the job's full name.
  Required-check configuration is keyed on it, so it must not encode a branch or build number.

`checkRun.key`::
  The checks API check name, which is already stable across the lifecycle of one check.

`externalId` (both suite and run)::
  `Run.getExternalizableId()`, i.e. one attempt per Jenkins build. Reporting a new `externalId`
  under the same key supersedes the previous attempt, which is what makes a rebuild replace the
  earlier result rather than sit alongside it. The queued report has no build yet and uses the job's
  full name, so it is superseded once the build starts.

`externalUpdatedAt`::
  Sent on every report, so that a stale retry cannot overwrite newer state.

`name` (both suite and run)::
  Display only; Origin never matches on it.

Pull requests are reported against the head of the pull request branch, never a merge commit: a
check on an ephemeral merge commit would not surface on the pull request.

=== Annotations

Annotations are a separate append-only sub-resource, addressed by the check-run id returned from the
upsert, and the endpoint is explicitly not idempotent. The publisher therefore sends them in the
batches of 25 that Origin accepts, stops at the 100-per-check-run cap (logging what it dropped), and
records how many it has already sent on the run so that a repeated report of the same check does not
duplicate them.

Origin has no equivalent of the checks API's images or actions, so those are dropped.

== Git Refspecs

=== Branches
Standard: `+refs/heads/*:refs/remotes/origin/*`

=== Pull Requests
No forks ⇒ no special PR refs needed. Use `+refs/heads/<headBranch>:refs/remotes/origin/<headBranch>`
and pin to the head SHA from PR metadata.

== Open Questions

[[_open_questions]]
. **Navigator repo listing API** — Resolved: use `GET /v1/origin/installation/repos`.
  This returns all repos the app installation is granted access to, regardless of whether
  the app is installed on individual repos or the whole team.
  The `repoOwner` field on the navigator is retained as a display label / owner filter
  (installations spanning multiple namespaces can be narrowed down).

. **`SCMProbe`** — Implemented as `OriginSCMProbe`.
  Uses `originServiceGetContents` to check for `Jenkinsfile` (or other criteria) without a full clone.
  Returns `NONEXISTENT` on 404, `REGULAR_FILE` for files, `DIRECTORY` for directories.

== Testing Plan

=== Integration tests — `MockOriginServer`

`MockOriginServer` (in `src/test/java`) runs an in-process `com.sun.net.httpserver.HttpServer`
that simulates the Origin REST API with real JWT-based authentication:

* The test generates a genuine Ed25519 key pair.
* `CursorOriginAppCredentials` signs a real JWT with the private key.
* The mock server verifies the JWT against the registered public key before issuing an `oit_` access token.
* All state (repos, branches, PRs, file presence) lives in memory, populated via a builder API.

`OriginSCMNavigatorTest` exercises five scenarios with `@WithJenkins` / `JenkinsRule`:

. **`singleRepoWithBranchesAndPR`** — two branches + one open PR → main + PR-1 discovered; PR head branch excluded from branch jobs.
. **`twoBranchesNoPRs`** — two branches, no PRs → both branch jobs created.
. **`organizationFolderDiscoversTwoRepos`** — `OrganizationFolder` + `OriginSCMNavigator` scans two repos → two multibranch projects.
. **`prHeadBranchExcludedFromBranchDiscovery`** — only branch is also PR head → PR appears, branch does not.
. **`noJenkinsfileProducesNoJobs`** — repo without Jenkinsfile → `OriginSCMProbe` returns NONEXISTENT → no jobs.

=== Checks tests

The checks classes are unit tested with a mocked `OriginSCMFacade`, which is the seam that keeps the
static Jenkins SCM and credentials lookups out of the way:

. **`OriginChecksDetailsTest`** — status, conclusion, timestamp, URL, output and annotation mapping,
  including the size limits and the contract violations that must be rejected.
. **`OriginChecksContextTest`** — repository, head SHA (branch, pull request head, queued build),
  suite and attempt identities, and each reason a job can be invalid.
. **`OriginChecksPublisherFactoryTest`** — which jobs are claimed, and that declining one is silent
  unless verbose logging was asked for.
. **`OriginStatusChecksPropertiesTest`** — defaults and `OriginChecksTrait` overrides.

`OriginChecksPublisherTest` asserts the requests actually put on the wire, using the real generated
API client against a WireMock-stubbed Origin API: the upsert body for each status, stable keys across
a check's lifecycle, annotation batching and capping, and that a rejected request is reported rather
than thrown.

`OriginChecksTraitITest` covers the Jenkins-side wiring with `@WithJenkins`: extension registration,
trait availability on an Origin source, a configuration round trip, and that a non-Origin job is left
to the other checks providers.

`CursorOriginAppCredentialsLiveTest` is a manual live test (requires env vars `ORIGIN_APP_PRIVATE_KEY_PEM`,
`ORIGIN_APP_ID`, `ORIGIN_APP_INSTALLATION_ID`) that mints a real token against the production
Origin API and verifies the credential `getPassword()` round-trip.
